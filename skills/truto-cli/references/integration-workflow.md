# Integration and mapping artifact workflow

Build, optionally edit the artifact, prepare, show the human the plan, then execute that plan on their approval. Reports and fresh checks are automatic.

```bash
truto integrations build https://docs.example.com/openapi.json acme
truto integrations apply acme.integration.json --prepare
# on the human's approval of the plan:
truto integrations apply acme.integration.json --plan acme.integration.json.plan.json --expect-digest <digest>
truto unified-mappings build acme crm --source-url https://docs.example.com/openapi.json
truto unified-mappings apply acme.crm.mappings.json --target base --prepare
# on the human's approval of the plan:
truto unified-mappings apply acme.crm.mappings.json --plan acme.crm.mappings.json.plan.json --expect-digest <digest>
```

An agent always takes this path. A plain `truto integrations apply <file>` has no prompt and writes live at once; a plain `truto unified-mappings apply` with no terminal or with `-o json`, and no `--yes`, writes nothing (exit 3).

Both builds save the exact checked candidate with a matching report and an authoritative `<artifact>.committed` pair. Edit only the artifact. Apply validates edited content against the projected live result before writing; a historical report never certifies later edits. A failure before an artifact exists has no invented output/report. Report commit failure preserves work and fails the run.

## Questions and confidence

Both builds now record a `confidence` (high/medium/low, information only -- it never blocks apply or publishing) and any open question, per method or cell, inside the matching report (also written as Markdown for people, e.g. `acme.integration.report.md`). A build that ends with something still waiting or blocked exits 3, not 0 (an integration build's `--fail-on none` is the one way to keep its own exit at 0 regardless; a mapping build, which has no `--fail-on`, exits 1 instead when a cell failed with an error and waits on no question). Answer with `build --continue <file> --answer id="…"` (repeatable) or `--answers <file>`; never the value itself for anything that looks like a credential -- it is refused outright. `--continue` rebuilds only what waited on the answered questions, spending no repair round, and refuses flags that change what is built (`--out`, `--docs-only`, `--only-missing`, `--resources`, …); a new gap the rebuild turns up waits on a new question, and so does an answered one whose gap still needs a change to the file (an unsupplied `{{value}}`, a list wrapper with no `response_path`, a file in a JSON body, or a list no example shows answered anything but a plain yes); other answered questions are not asked again. In a terminal, each build asks its own open questions itself before it finishes, instead of exiting with them unanswered (integration: at the very end, after refinement; mapping: before its refinement loop); Enter skips one and leaves it open.

## Optional inspection and prepared execution

```bash
truto integrations build --recheck acme.integration.json
truto unified-mappings build --recheck acme.crm.mappings.json
truto integrations apply acme.integration.json --dry-run
truto unified-mappings apply acme.crm.mappings.json --dry-run
truto integrations apply acme.integration.json --diff      # UPDATE only: how the file differs from live
truto integrations apply acme.integration.json --prepare
truto integrations apply acme.integration.json --plan acme.integration.json.plan.json --expect-digest <digest>
```

Recheck is offline and does not generate; it rewrites the file's `_build` marker when its known skips change. It releases an integration method or config value from a question the CLI asked (not one about a missing doc section) once its gap is fixed, even by an edit elsewhere (a credential field for a `{{value}}`); a list question only once no list check fires on the method. Apply never re-runs those checks: it keeps the hold while the held item is unchanged, so run the recheck after such a fix. An explicit integration `--spec <url>` still fetches the spec. An integration UPDATE artifact with no `.committed` gets its report refreshed but is not committed; apply recovers its baseline with a live read. Dry run performs no Truto reads, locks, local writes, platform writes or account tests; it reads the target as a real run does (the file's `id`, else the id an earlier apply recorded for it), stops with exit 3 where a real run stops on the name or on an `id` that reads as `.` or `..`, and reads a file with a leading byte-order mark like any other; merge/live checks remain unevaluated, and its audit uses the built-in category list (a category that list lacks only warns). It exits 0 unless input is unreadable (exit 1), except that an integration CREATE file (no `id`) with audit ERRORs or `--spec` violations exits 3 (next = `truto integrations lint <file>`) unless `--allow-audit-errors` / `--allow-spec-violations` (stricter than a real apply, which blocks a CREATE only on `--spec` violations and ERRORs about shared config); an UPDATE or `--docs-only` dry run only lists them (exit 0). An UPDATE dry run whose file drops a method its `.committed` baseline had exits 3 too, unless `--allow-method-removal` (offline, it cannot see whether live dropped the method as well). Use `truto integrations lint <file>` as the gate (it reads the category list, falling back to the built-in list, and for a file with an `id` that integration's live documentation rows for the orphan-row check, skipped with a notice when the read fails): it exits 1 on any ERROR or WARN (`--ignore-warnings`: on ERRORs only), while apply acts only on ERRORs (one about shared config blocks the apply; one naming a method skips that method). `--diff` (UPDATE only: the file needs its `id`) reads live and prints how the file differs from it (methods, other config sections, documentation rows); it writes and locks nothing and exits 0, or 1 on any failure (`-o json`: one document, `mode: "diff"`, with its `exit`). A modified method's `headers`, `authorization`, `query` and `body` are named, their values withheld. It is a two-way comparison while apply judges each difference against its last applied baseline (a teammate's live change is kept, a dropped method stops the run unless `--allow-method-removal`, a file with no baseline at all has its changes written over live, and a difference whose baseline cannot be recovered is a clash), so show the human `--prepare`'s plan, not the diff, as what will be written. Prepare reads and reconciles, commits locally and writes a plan (`--plan-out <path>` overrides the default, but may not be the artifact, another CLI-owned file, a directory, `-`, a path that is not a regular file, an existing file that is not a plan, or a path whose folder does not exist: exit 3, before anything is read or written); it does not write Truto or test an account. `--plan` executes only that plan and stops on stale inputs. The plan stores a `--spec` URL without its query string, so repeat the same `--spec` with `--plan` when the URL needs it. Mapping `--plan` requires `--expect-digest`.

Prepared plans retain the test account selected by `--test-account` or the profile, or no account if none was selected. Later profile changes do not switch that choice; run `--prepare` again to change the account.

## Concurrent changes, partial work and recovery

Apply compares the artifact, its trustworthy committed baseline and live. Unrelated live changes are preserved and synced into the file. A reported clash is resolved explicitly with `--resolve '<item>=mine'` or `--resolve '<item>=theirs'`; mine still runs every check and applies only to the recorded live value. A clash's `next` is the command that keeps the draft; to take live instead, run it with `=theirs` in place of `=mine` (an item named both ways is refused). An integration file with no baseline at all (no `.committed`, no `_build.source_version`, no `version` and `updated_at` from a `get -o json` dump: hand-written, or written by an older CLI without them) is written over live where they differ, as `--resolve '<item>=mine'` would, with a note; a live method it lacks counts as dropped (below) and a live config key it lacks stays live. A baseline the file names but apply cannot recover (a version gone from the history, a dump whose `updated_at` differs) still makes each difference a clash, and so does a mapping cell with no baseline. A different host/team/environment/integration or base/env target uses a separate working copy, preserving the original (a copy for another environment of the same team updates that team's integration by the file's `id`; like any copy it borrows no baseline, so its first apply writes the file over live where they differ); a `--plan` run, or a run that resolves no single team or environment while the committed state records one, stops instead (exit 3, nothing sent). `--prune-docs` never deletes the rows of a method that stays live (its removal held or skipped).

Eligible work can land while individual items are skipped, held, clashing, rejected or uncertain. A shared config/dependency issue can hold the config write; docs follow the method they describe. Mapping rows preserve authored fields and environment inheritance. Do not copy merged effective values into an authored override. All mapping-list pages must be read before assuming a row is absent. `db_info` is build context, not authority to overwrite live state.

Each write is reread. Lost responses and crashes retain enough state to reconcile a later run; never delete sidecars or add dummy edits to force retries. An editor save during the run is preserved. A live method the file drops or renames stops the whole integration apply before any write (exit 3, nothing written or committed, no plan) and is named in `blocked`, until `--allow-method-removal` or the method is back in the file (a mapping cell the file drops stays live instead: mapping apply never deletes rows); orphan doc rows stay live, listed as pending removals, until `--prune-docs` (exit 0); CREATE is private beta, and UPDATE never publishes or changes beta status. After a CREATE with `--slug-override`, apply writes the new `id` and the override as `name` into the artifact. A build whose output file is committed for another host/team/environment/integration stops (an integration build exits 1, a mapping build 3, as it does on a file that maps another integration, model or target with no `.committed`); pass another `--out`.

Apply exits 0 for complete/unchanged, 2 for landed writes with pending work (a write the platform answered 2xx for whose re-read failed counts as landed), 3 for blocked/nothing-written with pending work, 1 for auth/unexpected failure and 4 for an otherwise complete run with an executed test failure. `--prepare` writes nothing, so it exits 3 whenever its plan leaves something pending: read `blocked` (absent when the plan can run) and the items, not the exit code, before showing the plan. `-o json` emits one structured result. Dry run is a preview, not readiness proof.

## Documentation and repair

Changes to method verb/path, response path, body/body format, query/header placeholders, examples or pagination can refresh unedited docs during apply/prepare from recorded, grounded method regions and configured model access. Scopes/static headers make zero generation calls. Doc rows edited or deleted by hand stay yours, applied or not (a held removal, a clash): never regenerated or re-added; missing sources/models and failures retain existing rows with a reason. Global auth/pagination changes run deterministic cleanup and stale labels without broad generation. `integrations apply --no-docs-refresh` turns the refresh off: no model call or source fetch, each such method keeps its rows and is named in a note (`not regenerated: --no-docs-refresh; rows kept`), and the deterministic cleanup and labels still run; `--plan` and dry run never regenerate anyway.

Build/apply repairs share at most two rounds within the authorized run. A round can cover many methods; first-pass batching, truncation handling and bounded transport retries are not separate rounds. Confirmed unchanged-source gaps suppress repeated generation until relevant source/config/gap/model inputs change. Timeouts, malformed output and bad model configuration remain retryable. Explicit docs-only build refreshes docs in a separate `<slug>.docs.integration.json`; config is preserved exactly. Built from a file, its baseline is that file's own `.committed`; without one, rows the file held exactly as live did use that value and others are unknown (a teammate's live doc edit then clashes instead of being overwritten). Apply it with `--docs-only`. An instruction typed in a mapping build's refinement loop does not spend a repair round. A file with two documentation rows apply pushes of one identity (type, resource, method, authentication method) and different content is refused in every mode, dry run, `--diff`, prepare and `--docs-only` included (exit 3, `--diff` exit 1, before anything is written): keep one. Rows apply never pushes (`note`, `end_user_guide`, `tool_name`) may repeat.

## Eligible account reads

```bash
truto profiles set test-account.acme <account-id>
truto integrations apply acme.integration.json --test-account <account-id>
truto unified-mappings apply acme.crm.mappings.json --test-account <account-id>
```

The invocation account overrides the profile mapping. Marked accounts apply only when the token comes from the profile: an explicit `-p` beats `TRUTO_API_TOKEN`/`TRUTO_API_URL`, and a missing `-p` profile is an error. A mapping build samples only `--account`, the marked test account or an account picked at the prompt, never the profile's `defaultIntegratedAccount`. Use only the user's authorized target/account. Marking or testing discloses that reads can refresh tokens, change Truto reauth/forbidden state, emit ordinary auth/forbidden webhooks and affect sync jobs. Probes stop after the first provider 401 or failed refresh for an account; the first read goes alone, so a dead credential meets one 401. Provider mutations are never verification probes.

Every mapping sample and bootstrap call uses the shared effective-request safety gate; a `list`/`get` name or HTTP GET alone does not prove safety. It considers overrides, dependencies and evaluated request behavior. Unsafe/unproven reads are skipped. Within 30 minutes of a write to the integration or its environment integration row the account may still run its older cached config, so a mapping build (before its first live sample) and a read-only `integrations audit` (when a read would go) first refresh the config cache with `POST /integrated-account/refresh-mapping-cache` (the environment's cached mappings are cleared and the integration's connections reload their config) and wait about 7 minutes, less when the 30 minutes end sooner, counting down on stderr; later samples don't wait. If the refresh fails or misses some connections, or another write lands during the wait, nothing is sent until the latest write's 30 minutes end; the reason gives the time it can run again, and an audit that exercises nothing exits 1. Documentation examples can support independent work.

After its own fresh write, apply waits about 7 minutes after the cache refresh before reading; a test that does not fit the remaining run time, or follows another writer's change in the last 30 minutes, stays pending. Mapping apply re-checks failures recorded by build/recheck, reports a check whose live sample is gone as not run, and lists a cell the build could not produce as pending with its build command. Successful reads show a bounded transient terminal sample with credential and cursor fields withheld. Keep saved, applied, locally checked and live-tested distinct. Missing accounts, samples/inputs, runtime compatibility or exhausted time can leave checks explicitly not run. Even when reads execute, cache refresh is asynchronous and does not prove the served version: `version_confirmed=false` remains honest. Local JSONata success is not worker parity: versions/engine selection are unchanged. Never copy newly fetched provider records, credentials, bodies, debug envelopes or cursor values into reports/plans/committed state or repair prompts.

## Explicit restore and investigation

```bash
truto integrations get <id> --at-version <previous-version> -o json
truto integrations get <id> -o json
truto integrations update <id> --lock-version <current-version> --body-file restore.json --replace-config
truto docs get <doc-id> -o json
truto docs update <doc-id> --body-file doc-restore.json
```

Inspect old and current values first. `restore.json` contains a complete update body such as `{ "config": ... }`; `doc-restore.json` contains `{ "content": ... }`. `--body-file -` reads stdin. `--replace-config` acknowledges deliberate removals; `--merge-config` is for an intentional partial update. Under `--merge-config` a credential you name replaces the live one whole, so send the complete credential with its secret: one that lacks the live one's `format` or client id is refused, and so is a `credentials` that is not an object (null, a list) or is in the other shape from live's. The exception is an `oauth2`, `jwt_bearer` or `aws_sts` credential sent back under its key in the same format: the server keeps the stored fields you leave out, so a partial one is sent, and a format-less `{config: {…}}` is read as one legacy credential. Without a flag, a `credentials` sent as null or a list counts as an omitted key and is refused. `update --dry-run` prints what the config removes (`removed`: the first 200 names; `removed_count`: all of them), and a refused document says why (`reason`, `hint`) and names the credentials (`credentials`). Secret-preservation holds still apply, and on every host `update` holds (exit 3) a config that keeps a credential but leaves out a secret the read returned in plaintext (an `add-method --out` file never carries one; put it back from `truto integrations get <id> -o json`), and one that rewrites a legacy `credentials: {format, config}` as a keyed credential of the same method, with the same client id or none, without its client secret (the backend drops the legacy block, secret included); apply and add-method hold the same. Literal credentials belong outside build artifacts; affected writes stay held until the backend preservation prerequisite is verified on that host. Do not automatically revert live data. The same guard also fetches the live record (even with no `config`) whenever the body names `sharing` or `is_beta`, and refuses a change to either (exit 1) unless `--publish` is given; sending back the live value needs nothing, and `--publish` prints the change (`sharing: deny → allow`) before sending.

`truto logs --log-type unified_proxy_api --integrated-account-id <id> --all` follows bounded pages with a fixed end time. `--next-cursor <cursor>` resumes. API query failure is an error, not an empty success. Logs aid diagnosis but cannot prove which cached config version executed.
